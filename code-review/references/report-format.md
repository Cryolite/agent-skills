# 報告書の書式

レビュー結果の報告書の構成，各項目の書き方，指摘の分割と統合，採番，再レビューの書式を定める．報告書はすべて日本語で書き（句読点は「，」「．」を使う．[文体](#文体) を参照），[報告書検査スクリプト](../scripts/check_review_report.py) で検査する．

## 全体の構成

報告書は「コードレビュー結果」という見出しで始め，次の節をこの順に置く．節の見出しの文言は変えない（検査スクリプトが見出しの文言で節を識別する）．見出しのレベルは自由だが，各指摘の見出しは「指摘詳細」の見出しのちょうど一段下にし，「指摘詳細」の一段下には指摘の見出し以外を置かない．

| 節 | 要否 | 内容 |
|---|---|---|
| 概要 | 必須 | 対象，変更の目的，前提，実施した検証，判定，深刻度別の件数 |
| 前回指摘の対応状況 | 再レビューでは必須 | 前回までの指摘ごとの対応状況 |
| 指摘一覧 | 必須 | すべての指摘の一覧表 |
| 指摘詳細 | 必須 | 指摘ごとの詳細 |
| 確認事項 | 任意 | 指摘ではない質問 |
| レビューの範囲と限界 | 必須 | 精読した範囲，概観にとどめた範囲，実行できなかった検証など |

## 概要

```markdown
### 概要

- **対象**: ……
- **変更の目的**: ……
- **前提**: ……
- **実施した検証**: ……
- **判定**: ……

| 深刻度 | 件数 | 意味 |
|---|---|---|
| 高 | 1 | 解決するまでマージすべきでない（ブロッカー） |
| 中 | 2 | 未解決のままマージするには明示的なリスク許容の判断が必要 |
| 低 | 3 | 上記のいずれにも該当しない |
```

概要の 5 項目はすべて必須で，日本語で書く．

- **対象**: レビューした範囲を他の人が再現できるように書く．比較した ref とコミット，PR・MR の番号と head コミット，ファイル数，追加・削除行数，ファイル全体のレビューならそのパス．
- **変更の目的**: レビュアーが理解した変更の意図を 1〜3 文で書く．理解が誤っていれば作成者が気づけるようにするためである．ファイル全体のレビューでは，対象のコードの役割を書く．
- **前提**: 深刻度の判定に用いた前提（実行環境，入力の信頼性，利用者の範囲，アルゴリズムの実装なら照合した出典とその版など）．なければ「特になし」と書く．
- **実施した検証**: 実行したコマンドとその結果，再現実験の有無．何も実行しなかった場合は「なし」と書き，理由を添える．
- **判定**: 次のいずれかの語で書き始め，「 — 」に続けて理由を書く．

| 判定 | 条件 | 書き方の例 |
|---|---|---|
| マージ不可 | 「高」が 1 件以上 | マージ不可 — 深刻度「高」の指摘が 2 件あります． |
| 条件付きマージ可 | 「高」が 0 件で「中」が 1 件以上 | 条件付きマージ可 — 深刻度「中」の 3 件について，修正するか，リスクの許容を明示的に判断してください． |
| マージ可 | 「高」も「中」も 0 件 | マージ可 — 深刻度「高」「中」の指摘はありません． |

件数の表は，0 件の深刻度も含めて 3 行とも書く．見出し行と「意味」の列は上の例の文言のまま変えない．

## 指摘一覧

```markdown
### 指摘一覧

| ID | 深刻度 | 概要 | 場所 |
|---|---|---|---|
| R001 | 高 | 他人の注文を取り消せる | `src/shop/orders/views.py:52` |
```

- 指摘詳細と同じ順序で，すべての指摘を載せる．概要の列には指摘の見出しと同じ文言を書く．
- 場所の列には，指摘詳細の場所欄に書いた箇所のうち代表的な 1 箇所を同じ表記で書く．複数ある場合は「ほか 2 箇所」のように添える．
- 指摘が 1 件もない場合は，表の代わりに「指摘事項はありません．」と書く．

## 指摘詳細

各指摘は，見出しと項目の箇条書きで書く．

```markdown
#### R001【高】他人の注文を取り消せる

- **場所**: `src/shop/orders/views.py:52`（`cancel_order_view()`）
- **由来**: 変更起因
- **観点**: セキュリティ
- **確度**: 確定
- **問題**: ……
- **根拠**: ……
- **影響**: ……
- **深刻度の判断理由**: ……
- **修正案**: ……
```

見出しは `R001【高】概要` の形にする．概要は問題を具体的に表す一文（40 字程度まで，体言止めでもよい）とし，「バグがある」「修正が必要」のような中身の分からない書き方をしない．

項目は次の表の順に書く．項目名の表記は変えない．値が複数行にわたる場合（コード片など）は，項目の行の後に字下げして続ける．「問題」から「修正案」までの文章の項目は，コード片だけで済ませず日本語の説明を書く．

| 項目 | 高 | 中 | 低 | 内容 |
|---|---|---|---|---|
| 場所 | 必須 | 必須 | 必須 | 問題の箇所 |
| 由来 | ※ | ※ | ※ | 「変更起因」または「既存」 |
| 観点 | 必須 | 必須 | 必須 | 観点チェックリストの観点名 |
| 確度 | 必須 | 必須 | 必須 | 「確定」「ほぼ確実」「要確認」のいずれか |
| 問題 | 必須 | 必須 | 必須 | 何が誤っているか |
| 根拠 | 必須 | 必須 | 任意 | 問題が実在することを示す証拠 |
| 影響 | 必須 | 必須 | 任意 | 誰に，何が，どの程度起きるか |
| 深刻度の判断理由 | 必須 | 必須 | 任意 | その深刻度にした理由 |
| リスク許容時の対応 | 書かない | 必須 | 書かない | 許容してマージする場合の措置 |
| 修正案 | 必須 | 必須 | 必須 | 具体的な修正方法 |

※ 由来は，差分（未コミットの変更，ブランチ，コミット範囲，PR・MR）のレビューではすべての指摘に書き，ファイル全体のレビューでは書かない．

### 各項目の書き方

- **場所**: リポジトリのルートからの相対パスと行番号を `` `path:行` `` または `` `path:開始行-終了行` `` の形でバッククォートで囲み，関数名などを添える．複数の箇所は「，」で区切ってすべて列挙する．削除された行を指す場合は，変更前の行番号に「（変更前）」と添える．特定の行がない問題（テストの欠如など）は，関係するファイルや関数を示す．
- **由来**: 今回の変更が問題を持ち込んだ，既存の問題を到達可能にした，または悪化させた場合は「変更起因」．変更と無関係に以前からある問題は「既存」．どちらかの語だけを書く（補足が必要なら「既存（……）」のように括弧で添える）．
- **観点**: [観点チェックリスト](./checklist.md#観点名の一覧) の観点名を使う．複数あれば「，」で区切る．
- **確度**: 「確定」「ほぼ確実」「要確認」のいずれかの語で書き始める（補足は「確定（再現テストで確認）」のように括弧で添える）．「要確認」の場合は，問題となるための前提と，その確認方法を必ず続けて書く．
- **問題**: 何が誤っているかを，事実として簡潔に書く．
- **根拠**: 問題が実在することを示す証拠を書く．該当コードの引用（必要最小限），実行経路の説明，再現手順と結果，仕様やドキュメントとの対照など．アルゴリズムの実装では，出典の該当箇所（論文や書籍の版，ページ，節，式や疑似コードの行の番号）や公開コードの該当箇所（リポジトリ，コミット，パス，行番号）を示して対照する．確認した事実と推測を区別する．
- **影響**: 問題が起きたときに，誰に，何が，どの程度起きるか．発生条件も書く．
- **深刻度の判断理由**: [深刻度の判定基準](./severity.md#判断理由の書き方) に従う．
- **リスク許容時の対応**: リスクを許容してマージする場合に，責任者が判断するための情報と推奨される措置（フォローアップ issue の作成と期限，監視やアラートの追加，利用者への周知，暫定的な回避策など）を書く．
- **修正案**: 具体的な修正方法を書く．可能なら修正後のコード片を示す．選択肢が複数あれば，それぞれの得失を書く．修正に伴って追加すべきテストも書く．

## 指摘の分割と統合

原則として，一つの指摘は，独立に「修正する」「リスクを許容する」「指摘を却下する」を判断できる一つの問題とする．

次の場合は別の指摘に分ける．

- 根本原因が異なる．
- 修正方法が異なる，または別々の人やタイミングで直すことになる．
- 深刻度が異なる（例: 同じ検証漏れでも，外部から入力が届く箇所は「高」，内部からしか呼ばれない箇所は「低」）．
- 一方はリスクを許容できるが，他方はできない．
- 同じ行に独立した問題が複数ある（例: 境界条件の誤りと，例外の握りつぶし）．

次の場合は一つの指摘にまとめる．

- 同じ根本原因と同じ修正方法の問題が複数の箇所にある（例: 5 箇所の SQL の組み立てが，いずれも同じ方法でパラメータ化されていない）．場所欄にすべての箇所を列挙し，問題欄に件数を書く．
- 一つの修正で同時に解消する複数の症状（例: ある関数の引数検証の欠如によって生じる複数の不具合）．症状は影響欄に列挙する．

次のことは避ける．

- 重大な問題と軽微な指摘を一つにまとめる（軽微な指摘に紛れて重大な問題が見落とされる）．
- 機械的な繰り返し（同じ誤字が 10 箇所など）を 10 件に分けて件数を水増しする．
- 一つの問題を症状ごとに分け，同じ修正を複数の指摘で求める．

例:

- 「入力の検証が不足している」を 1 件にまとめかけたが，`/api/users` は認証なしで到達でき SQL インジェクションにつながる一方，`/admin/report` は管理者しか到達できず表示が崩れるだけだった → 2 件に分ける（前者は「高」，後者は「低」）．
- `parse_date()` のタイムゾーンの扱いの誤りが，3 つの呼び出し元で異なる症状を起こしている → `parse_date()` に対する 1 件にまとめ，症状を影響欄に列挙する．

## 採番

- ID は `R` と 3 桁以上の連番（`R001`，`R002`，…，`R999`，`R1000`，…）とする．
- 「高」「中」「低」の順に並べ，同じ深刻度の中では影響の大きい順，同程度ならパスと行番号の順に並べる．
- 初回のレビューでは，並べた順に `R001` から欠番なく番号を付ける．
- 一度付けた番号は，同じ会話の中で別の問題に再利用しない．取り下げた指摘の番号は欠番として残す．
- 指摘一覧，指摘詳細，確認事項，会話での言及のすべてで同じ ID を使う．

## 確認事項

指摘ではないが作成者に確認したいこと（意図，背景，仕様の不明点）を番号付きの箇条書きで書く．問題があることを示す具体的な根拠がある場合は，確認事項ではなく，確度「要確認」の指摘にする．確認事項がなければ節ごと省略してよい．

## レビューの範囲と限界

結論の確かさを読み手が判断できるように，次を書く．

- 精読した範囲と，概観にとどめた範囲（ロックファイル，生成物，ベンダー，バイナリなど）およびその理由
- 実行できなかった検証とその理由
- 参照できなかった情報（非公開の依存，外部システムの仕様，PR の議論，アルゴリズムの出典である論文や書籍，公開コードなど）
- その他，結論の確かさに影響する制約

## 再レビュー

修正後に改めてレビューする場合は，次のようにする．

- 前回の指摘のうち未解決または一部解決のものは，同じ ID のまま指摘詳細に載せる．深刻度は現状に合わせて見直してよい．
- 新しい指摘には，それまでに使った最大の番号の次から欠番なく番号を付ける（新しい指摘どうしは，深刻度と影響の大きい順に番号を付ける）．
- 「高」「中」「低」の順に並べ，同じ深刻度の中では ID の昇順に並べる．
- 「概要」の直後に「前回指摘の対応状況」を置く．

```markdown
### 前回指摘の対応状況

| ID | 前回の深刻度 | 状況 | 備考 |
|---|---|---|---|
| R001 | 高 | 解決済み | `a1b2c3d` で修正を確認しました． |
| R002 | 中 | 一部解決 | 2 箇所のうち 1 箇所が未修正のため，R002 として継続します． |
| R003 | 低 | 取り下げ | 呼び出し元で検証済みのため，問題ありませんでした． |
| R004 | 低 | 未解決 | 修正されていません． |
```

- 状況は「解決済み」「一部解決」「未解決」「取り下げ」のいずれかとする．
- 「一部解決」と「未解決」の指摘は指摘詳細に載せ，「解決済み」と「取り下げ」の指摘は載せない．
- これまでに付けたすべての ID（`R001` から最大の番号まで．過去の再レビューで解決済みや取り下げになったものも含む）を，この表に 1 行ずつ載せる．

## 文体

- 「です・ます」調で統一する．箇条書きの短い項目は体言止めでもよい．
- 句読点は「，」「．」を使い，「、」「。」は使わない．引用する原文（コード，メッセージ，文書）は句読点を変えずに，コードスパンかコードブロックで示す（検査スクリプトは，その外にある「、」「。」を警告する）．
- 確認した事実と推測を区別する（「〜です」と「〜と考えられます」「〜の可能性があります」）．確かめていないことを断定しない．
- 「〜した方がよいかもしれません」のような曖昧な書き方を避け，何をすべきかを具体的に書く．
- 作成者を責める書き方をしない．問題はコードについて述べる．
- コードの引用は必要最小限にとどめ，言語名を付けたコードブロックで示す．
- 秘密情報の値は伏せる（例: `AKIA` で始まるアクセスキー（以降は省略））．

## 記載例

### 指摘がある場合

````markdown
## コードレビュー結果

### 概要

- **対象**: `origin/main...HEAD`（merge-base `3f2a1b0`），3 ファイル（+96 / −2）
- **変更の目的**: 利用者が自分の注文を取り消す API（`POST /api/orders/<id>/cancel`）を追加し，取消時に在庫を戻すことと理解しました．
- **前提**: 本番環境の DB は PostgreSQL で，この API は認証済みの一般利用者に公開されます．
- **実施した検証**: `pytest tests/orders`（18 件すべて成功），`ruff check src tests`（指摘なし），一時ディレクトリでの再現テスト（R001 を確認）
- **判定**: マージ不可 — 深刻度「高」の指摘が 1 件あります．

| 深刻度 | 件数 | 意味 |
|---|---|---|
| 高 | 1 | 解決するまでマージすべきでない（ブロッカー） |
| 中 | 1 | 未解決のままマージするには明示的なリスク許容の判断が必要 |
| 低 | 2 | 上記のいずれにも該当しない |

### 指摘一覧

| ID | 深刻度 | 概要 | 場所 |
|---|---|---|---|
| R001 | 高 | 他人の注文を取り消せる | `src/shop/orders/views.py:52` |
| R002 | 中 | 同時に取消要求を受けると在庫が二重に戻る | `src/shop/orders/services.py:88-101` |
| R003 | 低 | 注文の状態を文字列リテラルで比較している | `src/shop/orders/services.py:88` ほか 1 箇所 |
| R004 | 低 | 取消のログから対象の注文を特定できない | `src/shop/orders/services.py:103` |

### 指摘詳細

#### R001【高】他人の注文を取り消せる

- **場所**: `src/shop/orders/views.py:52`（`cancel_order_view()`）
- **由来**: 変更起因
- **観点**: セキュリティ
- **確度**: 確定
- **問題**: 注文を `Order.objects.get(id=order_id)` で取得しており，その注文が要求した利用者のものかを確認していません．
- **根拠**: 52 行目は次のとおりです．

  ```python
  order = Order.objects.get(id=order_id)
  ```

  同じファイルの `order_detail_view()`（31 行目）は `Order.objects.get(id=order_id, user=request.user)` で所有者を限定しています．一時ディレクトリに作成した再現テストで，利用者 A のセッションから利用者 B の注文を指定して取消を要求すると，B の注文が取り消されることを確認しました．
- **影響**: 認証済みの利用者なら誰でも，注文 ID を変えるだけで他人の注文を取り消せます．注文 ID は連番で容易に推測できます．
- **深刻度の判断理由**: 一般の利用者が意図的に引き起こせ，取り消された注文は元に戻せないため「高」としました．
- **修正案**: 所有者で絞り込み，該当する注文がなければ 404 を返してください．

  ```python
  order = get_object_or_404(Order, id=order_id, user=request.user)
  ```

  あわせて，他人の注文の取消が 404 になることを確かめるテストを追加してください．

#### R002【中】同時に取消要求を受けると在庫が二重に戻る

- **場所**: `src/shop/orders/services.py:88-101`（`cancel_order()`）
- **由来**: 変更起因
- **観点**: 並行性，データ整合性
- **確度**: ほぼ確実
- **問題**: 状態の確認（88 行目）から更新（101 行目）までの間に排他制御がなく，同じ注文への取消要求が並行して処理されると，両方が「未取消」と判断して在庫を二重に戻します．
- **根拠**: `cancel_order()` は `transaction.atomic()` も `select_for_update()` も使っていません．クライアント（`web/src/api/orders.ts:45`）はタイムアウト時に同じ要求を最大 3 回再送するため，並行実行は現実に起こりえます．並行実行での再現は試みていません．
- **影響**: 在庫数が実際より多くなり，在庫のない商品を販売してしまうおそれがあります．不整合は夜間の棚卸しバッチまで検知されません．
````
