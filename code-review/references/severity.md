# 深刻度の判定基準

指摘の深刻度を「高」「中」「低」に分類するための基準．迷ったときは，まず [定義](#定義) に立ち返る．

## 定義

| 深刻度 | 定義 |
|---|---|
| 高 | その問題が解決されるまで，ソースコード群のマージを行うべきではない（ブロッカー）． |
| 中 | その問題を解決しないままマージを行う場合には，リスクの許容に関する明示的な判断が必要である． |
| 低 | 「高」にも「中」にも分類されない． |

- 「解決」とは，問題を修正すること，または問題でないことを根拠をもって示すこと（確度「要確認」の指摘で，前提が成り立たないと確認できた場合など）をいう．
- 「明示的な判断」とは，マージの責任者（メンテナー，テックリード，リスクの所有者など）がリスクの内容を理解したうえで許容すると決め，その判断を記録に残すこと（PR・MR のコメント，フォローアップ issue など）をいう．レビュアー（このスキル）がリスクを許容することはない．
- 既存コード全体やファイル単位のレビューのように，レビュー対象の「マージ」がない場合は，そのコードがいまマージ要求として提出されたと仮定して判定する．

## 判定の手順

1. **問題を具体化する．** 発生条件，到達経路，結果，影響範囲を一文で書けるようにする．書けないなら，まだ指摘にできる段階ではない（SKILL.md の手順 6 に戻る）．
2. **「高」かを判定する．** 次の両方を満たすなら「高」とする．
   - 問題が残ったままマージされると，現実的に起こりうる状況（通常の利用や運用，または攻撃者が意図的に作り出せる条件）で，受け入れられない結果が生じる．
   - 事情を知った合理的なレビュアーなら，修正前のマージを認めない．
3. **「中」かを判定する．** 「高」でなく，次のいずれかに当たり，かつマージするならそのリスクを誰かが承知している状態にすべきだと言えるなら「中」とする．
   - 具体的な損害につながりうるが，発生条件が限られる，影響が限定的または回復可能である，あるいは他の手段で緩和されている．
   - いま損害がなくても，退行を検出できない，障害の調査を困難にする，将来の変更で事故を招きやすいなど，具体的に説明できるリスクがある．
4. **それ以外は「低」とする．**

## 判定に使う要素

| 要素 | 深刻度を上げる方向 | 深刻度を下げる方向 |
|---|---|---|
| 影響の大きさ | データの消失・破損，セキュリティ侵害，金銭的損失，全利用者に及ぶ停止 | 表示の乱れ，軽微な不便，開発者だけが影響を受ける |
| 発生可能性 | 通常の経路で必ず起きる，外部から誘発できる | 極めてまれな条件の組み合わせが必要 |
| 検出の容易さ | 気づかれないまま誤った結果が残る（サイレントな破損） | すぐに明確なエラーとして表面化する |
| 回復の容易さ | 不可逆（削除済み，送信済み，公開済み） | 再実行やロールバックで容易に戻せる |
| 影響範囲 | 公開 API，共有ライブラリ，多数の利用者，本番環境 | 内部ツール，試作，限られた利用者 |

修正の手間（簡単に直せるかどうか）や，指摘の種類（「セキュリティだから高」「スタイルだから低」）だけで深刻度を決めない．

## 典型例

典型例は目安にすぎない．同じ種類の問題でも，影響と文脈によって深刻度は変わる（例: 誤字でも，設定キー名や公開 API 名の誤字で動作が変わるなら「高」になりうる）．

### 「高」の典型例

- 通常の使い方で誤った結果，クラッシュ，ハング，無限ループを引き起こすバグ
- データの消失，破損，不整合を引き起こしうる処理（誤った削除条件，トランザクションの欠如による不整合，元に戻せないマイグレーションの誤り）
- 悪用可能な脆弱性（インジェクション，認証や認可の欠落・回避，パストラバーサル，安全でないデシリアライズ，XSS，SSRF など）
- 秘密情報（パスワード，API キー，秘密鍵，トークン）のコミットや，ログ・エラーメッセージへの出力
- ビルド，型検査，既存のテスト，CI を壊す変更
- 公開 API，CLI，設定，ファイル形式，DB スキーマの，予告や移行手段のない互換性の破壊
- 変更の目的そのものを達成していない，または仕様と明確に矛盾している
- 通常の負荷でタイムアウトや資源の枯渇を招く性能上の問題（現実的なデータ量での計算量の爆発，上限のないメモリ消費）
- 本番環境で現実的に発生する競合状態やデッドロック
- ライセンス上，配布や利用が許されないコードや依存の追加
- 論文や書籍などのアルゴリズムの実装が出典の理論や疑似コードと食い違い，通常の入力で誤った結果を返す，または利用者が依存する保証（最適性，収束，計算量など）が成り立たない（数式の符号や添字の誤り，更新の順序の取り違え，終了条件の誤り）

### 「中」の典型例

- 特定の条件（まれな入力，特定の環境，高負荷時，障害時）でだけ発生し，影響が限定的または回復可能な不具合
- 障害時に原因の特定を困難にする，または中途半端な状態を残しうるエラー処理の不備
- 新しい重要なロジックに対するテストの欠如や，退行を検出できないテスト
- 悪用に追加の条件が必要な脆弱性，多層防御の欠落，安全でない既定値
- 規模の拡大に伴って問題になる性能上の懸念
- 誤用を招きやすい API 設計や，誤解を招く命名・ドキュメントで，実害につながる具体的な経路があるもの
- サポートが終了した，または移行期限が迫っている非推奨の API や依存の使用
- 運用上の懸念（ログや監視の不足，ロールバックが困難な変更，設定値の検証不足）
- 将来の変更で不具合を招きやすい重大な設計上の負債（同じロジックの重複による修正漏れの危険など）
- 論文や書籍などのアルゴリズムの実装で，出典の前提条件を満たさない入力や数値的に厳しい入力（極端な値，悪条件の行列）に対してだけ，誤った結果を黙って返すもの
- 結果の再現性や公開コードとの比較が重要な場合に，それを損なう記録されていない差異（既定値，安定化の項，初期化などの違い）

### 「低」の典型例

- 可読性の改善（命名，構造，コメント，複雑さの低減）
- リポジトリの規約からの軽微な逸脱（自動整形で直るもの，表記の揺れ）
- 実害のない冗長なコード，未使用の変数や import
- 誤字や脱字，ドキュメントの軽微な不正確さ
- より簡潔，または慣用的な書き方の提案
- 効果がごく小さい性能改善の余地
- 出典（書誌情報，版，式や疑似コードの番号）の記載漏れや，出典の記法と変数名の対応の分かりにくさ

## 境界事例

### 既存の問題（差分のレビュー）

- 今回の変更が問題を持ち込んだ場合に加え，既存の問題を到達可能にした，影響を拡大した，または悪化させた場合も「変更起因」として通常どおり判定する．
- 変更と無関係に以前からある問題は「既存」とする．マージしても状況は悪化しないため，原則として「高」にはしない．放置すると重大な損害につながるものは「中」とし，「リスク許容時の対応」に別途の対応（issue の作成など）を書く．それ以外は「低」とする．
- ただし，マージが即座にリリースや配布につながり，その既存の問題を含んだまま出荷することが明らかに受け入れられない場合など，マージを止める合理的な理由があれば「高」としてよい．その理由を判断理由に明記する．
- 既存の問題の探索に時間を費やしすぎない．変更を理解するために読んだ範囲で気づいたものを報告する．

### 確度が「要確認」の指摘

- 前提が成り立つ場合の影響で深刻度を判定し，その前提と確認方法を明記する．
- 「高」かつ「要確認」の指摘は，修正するか，前提が成り立たないことを確認するまでブロッカーとして扱う．
- 手元で確かめられる前提（コードの検索，設定の確認，実行）は，報告する前に確かめる．確かめられず，判定に大きく影響する場合は，ユーザに質問する．

### 判断が分かれる場合

- 二つの深刻度の間で迷う場合は，判断理由に両方の見方と決め手を書いたうえで，より慎重な（高い）方を選ぶ．ただし，根拠のない可能性だけで深刻度を上げない．
- 前提（本番か試作か，入力が信頼できるかなど）によって深刻度が変わる場合は，採用した前提を報告書の「前提」と判断理由に書く．

### 複数箇所にまたがる問題

- 同じ根本原因の問題を一つにまとめる場合でも，深刻度が異なる箇所は別の指摘に分ける．最も深刻な箇所に合わせて全体を「高」にしたり，軽い箇所に合わせて全体を「低」にしたりしない．
- 「低」の指摘がいくつあっても，それだけで「中」に格上げしない．ただし，繰り返しが具体的なリスクを生んでいる場合（例: 同じ検証漏れが多数の入口にある）は，そのリスクを一つの指摘として評価する．

### テストコード，ドキュメント，設定だけの問題

- テストの誤りによって退行を検出できない状態になるなら「中」．常に成功する偽のテストによって重要な機能が実質的に無検証になる場合や，CI を壊す場合は「高」となりうる．
- ドキュメントの誤りによって利用者が誤った操作をし，損害（データの消失，誤ったセキュリティ設定など）を受けうるなら「中」以上．それ以外は「低」．
- 設定の誤りは，その設定が本番で使われるかどうかで判断する（例: 本番用の設定での TLS 証明書検証の無効化は「高」）．

### 自動ツールの警告

- ツールが警告したこと自体は深刻度を決めない．内容を検証し，実際の影響で判定する．
- CI で失敗として扱われる警告（`-Werror`，linter のエラー設定など）を新たに生む変更は，CI を壊すため「高」とする．

### 試作や検証用のコード

- 利用者や寿命が限られることが明確なら，堅牢性や保守性の問題の深刻度は下がりうる．その場合は前提として明記する．
- 秘密情報の漏洩や，試作が本番データ・本番環境に触れることによる危険は，試作であっても深刻度を下げない．

### 出典との差異（論文や書籍などのアルゴリズムの実装）

- 出典と異なることだけを理由に深刻度を決めない．差異が結果の正しさ，理論が保証する性質，再現性に与える影響で判定する．
- 出典より正しい，または出典と等価な実装（正誤表に基づく修正，数値的に安定な等価変形）は問題としない．差異とその理由が記録されていなければ記録の不足を指摘する（通常は「低」．差異を知らない人が出典どおりに戻すと誤りが再発するなど，具体的なリスクがあれば「中」）．
- 出典自体が誤っていると考えられる場合（本文と疑似コードの矛盾，正誤表に載っている誤り）は，実装が出典どおりでも，誤った結果を招くなら通常どおり判定する．出典の誤りを確かめられない場合は確度を「要確認」とし，前提（出典のどの記述が誤っているか）と確認方法を書く．
- 試作や研究用のコードでも，出典の結果の再現や比較が目的であれば，結果を変える差異の深刻度を下げない．

## 判断理由の書き方

「深刻度の判断理由」には次を含める．

- 判定の決め手（影響，発生条件，発生可能性，検出や回復の容易さ）
- 一段上（または下）の深刻度にしなかった理由
- 採用した前提（あれば）

例（「中」の場合）:

> 不正な形式の行が 1 行でもあると，その行以降の取り込みが黙って打ち切られ，データの欠落に気づけません．ただし入力ファイルは社内のバッチが生成するもので，これまで形式の誤りは発生していないため，通常の運用で起きる可能性は低いと判断し，「高」にはしませんでした．欠落は再取り込みで回復できますが，検知する仕組みがないため，未修正のままマージするにはリスクの許容に関する判断が必要です．

例（「高」の場合）:

> 認証済みの利用者であれば誰でも，注文 ID を変えるだけで他人の注文を取り消せます．注文 ID は連番で推測が容易なため，悪意のある利用者が実際に悪用できます．取消は返金と在庫の戻しを伴い元に戻せないため，修正前にマージすべきではありません．
