# コードレビュー

ソースコード群（差分，ブランチ，プルリクエスト，ファイル，リポジトリ全体）を極めて詳細かつ精緻にレビューし，発見した問題を深刻度「高」「中」「低」に分類して，`R001` から始まる通し番号付きの報告書として日本語で提示する．

## 基本原則

- **出力はすべて日本語で，句読点は「，」「．」を使う．** 報告書，途中経過の説明，ユーザへの質問とその選択肢を日本語で書き，「、」「。」は使わない．ユーザが他の言語で依頼した場合も同じ．コード片，識別子，パス，コマンド，ツールやコンパイラのメッセージは原文のまま（句読点も変えずに）引用する．
- **レビューに徹する．** レビュー対象のファイルを変更しない．インデックス，作業ツリー，ref，履歴を変更する git 操作（`add`，`commit`，`checkout`，`switch`，`restore`，`reset`，`stash`，`merge`，`rebase`，`pull`，`push` など）をしない．`git fetch` や `git worktree add` が必要なときは事前にユーザの了承を得る．整形ツールや linter を書き込みモード（`--fix`，`--write`，`-w` など）で実行しない．PR・MR へのコメント投稿や状態の変更は，ユーザが明示的に依頼した場合に限る．
- **一時ファイルはリポジトリの外に置く．** 再現用のコードや作業メモは `mktemp -d` で作った一時ディレクトリに置き，作業の終わりに削除する．
- **根拠のある指摘だけを報告する．** すべての指摘は，実際に読んだコードと具体的な失敗シナリオ（どの入力・状態で，どの経路を通り，何が起きるか）に基づかせる．ファイル名，行番号，API の挙動を推測で書かない．
- **網羅する．** 対象の変更行はすべて読み，[観点チェックリスト](./references/checklist.md) の全観点を適用する．問題を数件見つけた時点で打ち切らず，抜き取り確認で済ませない．
- **反証してから報告する．** 各候補について，呼び出し元の検証，フレームワークや型システムの保証，不変条件，既存のテストなどによって問題が起きない可能性を検討し，否定できたものは報告しない．誤検知はレビュー全体の信頼を損なう．
- **リポジトリの規約と文脈に従う．** スタイルや設計の良し悪しは，レビュアーの好みではなく，リポジトリの規約，既存コードの慣習，設定済みのツールに照らして判断する．
- **秘密情報を拡散しない．** 認証情報などを見つけた場合は場所と種類を報告し，値そのものは伏せる．

## 深刻度

| 深刻度 | 意味 | マージ判断への影響 |
|---|---|---|
| 高 | その問題が解決されるまでマージすべきでない（ブロッカー） | 修正されるか，問題でないことが確認されるまでマージ不可 |
| 中 | 未解決のままマージするには，リスクの許容に関する明示的な判断が必要 | 修正するか，責任者がリスクの許容を明示的に判断すればマージ可 |
| 低 | 「高」にも「中」にも該当しない | マージ判断に影響しない |

次の順に判定する．詳細な基準，典型例，境界事例は [深刻度の判定基準](./references/severity.md) に従う．

1. 問題が残ったままマージされると，現実的に起こりうる状況で受け入れられない結果（誤動作，クラッシュ，データの消失や破損，セキュリティ侵害，ビルド・テスト・CI の破壊，予告のない互換性の破壊，ライセンス違反など）を招き，事情を知った合理的なレビュアーならマージを認めないか → **高**
2. 具体的なリスク（発生条件の限られた不具合，性能や運用上の懸念，退行を検出できないテスト不足，将来の変更で事故を招きやすい負債など）があり，マージするなら誰かがそのリスクを承知のうえで許容すると明示的に判断すべきか → **中**
3. いずれでもない → **低**

深刻度は修正の手間や指摘の件数ではなく，影響の大きさ，発生可能性，検出や回復の容易さ，プロジェクトの文脈で決める．

## 手順

### 1. レビュー対象を確定する

依頼内容から対象を決め，同梱のスクリプトで対象ファイルと変更箇所の一覧を作る．

| 依頼の例 | 対象 | サブコマンド |
|---|---|---|
| 「この変更を」「今の作業を」 | 未コミットの変更（未追跡ファイルを含む） | `worktree` |
| 「ステージした分を」 | ステージ済みの変更 | `staged` |
| 「このブランチを」「マージ前に」 | ベースとの merge-base から HEAD まで | `branch [BASE]` |
| 「`a1b2c3d` を」「`v1.2..v1.3` を」 | コミット，コミット範囲 | `commit REV`，`range A..B` |
| 「`src/auth/` を」「リポジトリ全体を」 | ファイル全体 | `files [PATH...]` |
| 「PR #123 を」「!45 を」 | プルリクエスト，マージリクエスト | 下記「PR・MR の場合」 |

```sh
python3 ~/.agents/skills/code-review/scripts/list_review_targets.py detect
python3 ~/.agents/skills/code-review/scripts/list_review_targets.py branch origin/main
```

このスキルを別の場所に置いた場合は，`~/.agents/skills/code-review` をそのディレクトリに読み替える．

- 対象が明示されていなければ `detect` を実行する．「ユーザへの確認: 必要」と表示されたら，示された候補を選択肢としてユーザに日本語で質問する（質問用のツールがあればそれを使う）．「不要」なら 1 番目の候補を使う．依頼の文言（「コミット前に」など）から別の候補が明らかに適切な場合は，そちらを使う．
- `-- PATH...` を付けると対象を絞り込める．`--json` で JSON を出力する．
- 出力の「変更行（変更後）」は変更後のファイルでの行番号であり，精読の進捗管理に使う．分類ごとに次のように扱う．
  - ソース，テスト，ビルド・CI，依存関係，設定，ドキュメント: 全行を精読する．
  - ロックファイル，生成物，ベンダー: 概観する（追加・削除された依存とその取得元，生成元との整合，手作業による編集の痕跡，不要な混入）．生成物と推定されたファイルが本当に生成物か（生成元や生成手順があるか）も確かめる．
  - バイナリ，シンボリックリンク，サブモジュール: 存在と参照先の妥当性（意図した追加か，サイズ，リンク先，参照するコミット，秘密情報やライセンスの懸念）を確認する．
- 「注意」欄（秘密情報らしき文字列，競合マーカー，デバッグ用コード，実行権限の変更など）は機械的な検出結果である．必ず該当箇所を読んでから指摘にするか判断する．
- ユーザが重点観点（例: セキュリティ）を指定した場合は，その観点を特に深く調べる．ただし範囲を明示的に限定されない限り，他の観点も省略しない．
- 変更が大きすぎて一度に精読しきれない場合は，黙って範囲を狭めず，分割の方針（ディレクトリ単位など）をユーザに提案して確認する．

**PR・MR の場合**: `git remote get-url origin` でホスティング先を判別する．GitHub なら GitHub MCP サーバのツール（`pull_request_read` の `get`，`get_diff`，`get_files`，`get_comments`，`get_review_comments` など）か `gh pr view <番号> --comments`，`gh pr diff <番号>` を，GitLab なら GitLab MCP サーバのツールか `glab mr view <番号> --comments`，`glab mr diff <番号>` を使い，説明文，関連 issue，既存のレビューコメントも読む．変更後のファイル全体は，head コミットが手元にあれば `git show <sha>:<path>` で読み，なければ MCP のファイル取得ツールを使うか，`git fetch` の了承をユーザに求める．PR のブランチをチェックアウトしない．

### 2. 意図，前提，規約を把握する

- 変更の意図: ユーザの説明，PR・MR の説明と議論，関連 issue，コミットメッセージ（`git log --format='%h %s%n%n%b' <base>..HEAD`），関連する仕様書や設計文書，テスト．
- 規約: `README`，`CONTRIBUTING`，`AGENTS.md`，`CLAUDE.md`，`.github/copilot-instructions.md`，スタイルガイド，linter・formatter・型検査の設定，CI 定義（どの検査が自動で実行されるか），`SECURITY.md`，ADR．
- 文脈: 成果物の種類（ライブラリ，サービス，CLI，試作など），実行環境，サポート対象のバージョンやプラットフォーム，公開 API の範囲，信頼境界（誰が入力を与えうるか）．深刻度に影響する前提が分からなければ，ユーザに確認するか，合理的な前提を置いて報告書の「前提」に明記する．
- 使われている言語や技術について，[言語・技術別の着眼点](./references/language-pitfalls.md) の該当する節を読む．
- 論文や書籍などに記述されたアルゴリズムを実装している場合は，出典（論文や書籍の該当箇所，疑似コード，正誤表，著者などが公開しているコード）を特定して読み，照合に使う版（論文や書籍の版，公開コードのコミット）を記録する．出典を特定または入手できなければ，ユーザに提示を求める．公開されている論文やコードは Web で参照してよいが，レビュー対象のコードを外部に送らない．公開コードを取得（`git clone` など）して実行する場合は，事前にユーザの了承を得る．参照できなかった出典は報告書の「レビューの範囲と限界」に書く．

### 3. 自動検証を実行する（安全な範囲で）

- CI 定義，`Makefile`，`package.json` の scripts，`pyproject.toml`，`tox.ini` などから，プロジェクト標準の検査コマンドを特定する．
- コンパイル，型検査，linter（検査モード），テストのうち，対象を変更せず外部に副作用を及ぼさないものを，変更との関係が深いものから実行する．
- 依存パッケージのインストール，ネットワークや外部サービス（DB，コンテナ，クラウド）を使うもの，長時間かかるもの，リポジトリ内に想定外の書き込みをするものは，事前にユーザの了承を得る．実行できなかった検証は報告書の「レビューの範囲と限界」に書く．
- ツールの出力は指摘の候補にすぎない．手順 6 で検証し，同じ基準で深刻度を判定する．変更と無関係な既存の警告を「変更起因」として報告しない．
- 実行したコマンドと結果を，報告書の「実施した検証」に書く．

### 4. 精読する

- 対象一覧のファイルを，中核のロジック，それが依存する部分，テスト，ビルド・設定，ドキュメントの順に一つずつ読む．
- 各変更箇所について，それを含む関数やクラスの全体を読み，必要に応じてファイル全体，変更前の版（`git show <base>:<path>`），呼び出している関数の定義，変更された関数・型・定数のすべての利用箇所（`grep` や言語サーバで探す）を読む．シグネチャや意味が変わった場合は，テスト，ドキュメント，設定，他言語のコードを含むすべての利用箇所を確認する．
- 削除されたコードについては，残っている参照（コード，ドキュメント，設定，スクリプト）を探す．追加されたファイルは全体を読む．
- [観点チェックリスト](./references/checklist.md) の全観点を各変更箇所に適用する．
- 論文や書籍などのアルゴリズムの実装は，出典の数式や疑似コード，公開コードと一行ずつ対応付けて読み，[理論的整合性，疑似コードとの整合性，公開コードとの整合性](./references/checklist.md#論文書籍などのアルゴリズムの実装) を確かめる．
- 気づいた候補は，その場で場所と一行の仮説を作業メモに記録する．読み終えた変更箇所も記録し，最後に未読の箇所が残っていないことを確かめる．
- 行番号は推測せず，行番号付きでファイルを表示して確かめる．変更後の行番号を使い，削除された行は変更前の行番号に「（変更前）」と添える．

### 5. 変更全体を横断的に確認する

個々の行を読むだけでは見えない問題を探す．

- 意図した目的を達成しているか．必要な変更（テスト，ドキュメント，マイグレーション，設定，CHANGELOG，連動して変えるべき箇所）が欠けていないか．
- 対になる箇所が整合しているか（API とクライアント，スキーマとモデルとマイグレーション，シリアライズとデシリアライズ，生成側と消費側，ドキュメントと実装，新しい列挙値を扱うべきすべての分岐）．
- 信頼できない入力が，検証や無害化をされないまま危険な処理（SQL，シェル，ファイルパス，HTML，デシリアライズ，URL，ログ）に到達しないか．
- 互換性（公開 API，CLI，設定，ファイル形式，通信プロトコル，DB スキーマ，新旧バージョンの混在，ロールバック）．
- 失敗時の挙動（部分的な失敗，再試行，タイムアウト，冪等性，後始末），並行実行，現実的なデータ量での性能，運用（ログ，監視，設定の既定値，段階的な展開）．
- テストが新しい挙動と境界・異常系を検証しているか．コードが壊れたときに実際に失敗するテストか．

### 6. 候補を検証する

候補ごとに次を行う．

1. 指摘する場所のコードを読み直し，ファイル名と行番号を確かめる．
2. 具体的なシナリオ（入力や状態 → 実行経路 → 誤った結果 → 影響）を組み立てる．
3. 反証を試みる．呼び出し元，ミドルウェア，フレームワーク，型，DB の制約，設定，既存のテストが問題を防いでいないかをコードベースで確かめる．
4. 安全かつ実用的であれば，リポジトリ外の一時ディレクトリで最小の再現コードを実行するか，既存のテストを特定の入力で実行して確かめる．アルゴリズムの実装では，出典の数値例，理論が保証する性質（不変条件，最適性など），公開コードの出力との比較も使える．
5. 判定する．反証できた候補は捨てる．問題であれば確度を付けて指摘とする．問題かどうかが意図や仕様しだいで，問題を示す具体的な根拠がなければ「確認事項」とする．

| 確度 | 意味 |
|---|---|
| 確定 | 実行して再現した，またはコード上で反論の余地なく示せる |
| ほぼ確実 | コード上の根拠が明確で反証もできなかったが，実行による確認はしていない |
| 要確認 | 手元で確かめられない前提（仕様の意図，本番の設定，外部システムの挙動など）が成り立つ場合に問題となる |

### 7. 指摘を整理する

- **分割と統合**: 一つの指摘は「独立に修正，リスク許容，却下を判断できる一つの問題」とする．根本原因，修正方法，深刻度，判断の主体のいずれかが異なれば別の指摘に分ける．同じ箇所に独立した問題が複数あれば分ける．同じ根本原因と修正方法の問題が複数箇所にあれば一つにまとめ，すべての場所を列挙する（場所によって深刻度が異なれば深刻度ごとに分ける）．重大な問題と軽微な指摘を一つにまとめない．詳細と例は [報告書の書式](./references/report-format.md#指摘の分割と統合) を参照する．
- **深刻度と由来**: 深刻度を判定して判断理由を書く．差分のレビューでは，各指摘の由来を「変更起因」（今回の変更が持ち込んだ，到達可能にした，または悪化させた問題）か「既存」（変更と無関係に以前からある問題）とする．
- **並べ替えと採番**: 「高」「中」「低」の順に並べ，同じ深刻度の中では影響の大きいものから，同程度ならパスと行番号の順に並べる．並べた順に `R001`，`R002`，… と欠番なく番号を付ける（3 桁のゼロ埋め．`R999` の次は `R1000`）．

### 8. 報告書を作成して検証する

[報告書の書式](./references/report-format.md) に従って報告書を書き，リポジトリ外の一時ファイルに保存して，同梱の検査スクリプトにかける．

```sh
python3 ~/.agents/skills/code-review/scripts/check_review_report.py --kind diff \
  --root "$(git rev-parse --show-toplevel)" "$tmpdir/report.md"
```

- `--kind` には，差分（未コミットの変更，ブランチ，コミット範囲，PR・MR）のレビューなら `diff`，ファイル全体のレビューなら `files` を指定する（「由来」の要否を検査する）．
- `--root` は，作業ツリーがレビュー対象の変更後の状態と一致する場合にだけ付ける（場所欄のパスの存在と行番号の範囲を検査する）．再レビューでは `--rereview` を付ける．
- エラーはすべて直す．警告は直すか，妥当な理由を確かめたうえで許容する．Python 3 が使えない場合は，書式を目視で確認する．
- 検査に通った報告書の全文をユーザに提示する（一時ファイルのパスだけを示さない）．

### 9. 提示後の対応

- 個々の指摘への質問には ID を挙げて答える．反論を受けたら再検証し，誤りであれば取り下げを明言する．番号は振り直さない．
- 修正後の再レビューでは，前回の指摘には同じ ID を使い続け，新しい指摘にはそれまでに使った最大の番号の次から欠番なく番号を付ける．番号は再利用しない．報告書に「前回指摘の対応状況」を設け，それまでに付けたすべての ID の対応状況を載せる．
- このスキルではコードを修正しない．ユーザが修正を明示的に依頼した場合は別の作業として行い，修正後に改めてレビューする．

## 報告書の骨子

```markdown
## コードレビュー結果

### 概要
```
